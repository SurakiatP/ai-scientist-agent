# Public API, API Keys, Python SDK and MCP Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Other systems and AI agents can run research on the platform through a documented REST API (OpenAPI), a small Python SDK, and an MCP server, all authorized by operator-issued API keys (TOR §2 "เชื่อมต่อและเรียกใช้แพลตฟอร์มได้ผ่านมาตรฐานเปิด ได้แก่ REST API และ MCP"; TOR v1.0 §5.1 จ).

**Architecture:** API keys live in a new `api_keys` table (only a SHA-256 hash is stored; keys are 256-bit random, so a fast hash is correct) and are created/listed/revoked by an operator CLI — no sign-up page, no web login (standing constraint). A new router under `/v1/api` requires `Authorization: Bearer <key>`; it wraps the existing run service: `POST /v1/api/research` creates a session + turn in a dedicated "API" project and submits a run with `client_id = "key:<key id>"` (fair queueing per key); the run, its SSE events, cancel and artifacts are read through the same RunService and store. The MCP server (official `mcp` Python SDK, FastMCP, Streamable HTTP) is mounted at `/mcp` and calls the same functions with the same bearer key. The Python SDK is a single-module httpx client in `sdk/python`.

**Tech Stack:** FastAPI, SQLAlchemy/Alembic, `mcp` (pinned), httpx, pytest.

**Spec:** `docs/superpowers/specs/2026-10-29-production-roadmap.md` (plan 9). Deviations (ruled): MCP auth uses the same bearer API keys instead of OAuth 2.1 (no identity provider exists; standing no-login constraint); the TOR's `approve` tool maps to `start_research(question, plan=...)` after `plan_research` (runs here never pause mid-way for approval); `ask_lab` and `list_skills` become `list_packs` (the platform's skill selection is the field pack); A2A stays out of scope.

## Global Constraints

- Key format `sci_` + 43-char urlsafe base64 of 32 random bytes (`secrets.token_urlsafe(32)`); stored: `id` (uuid), `name` (≤ 80), `prefix` (first 12 chars of the key, shown in listings), `hash` (sha256 hex, unique), `created_at`, `revoked_at`, `last_used_at`. The full key is printed exactly once by the CLI and never logged, stored or returned by any endpoint. Migration `0008_api_keys`.
- CLI: `uv run --project backend python -m scientist.apikeys create --name "<name>"` | `list` | `revoke <prefix>`; uses `DATABASE_URL` like the app; `list` never shows hashes. Documented in `docs/deploy.md` and `docs/api.md`.
- Auth dependency: missing/malformed/unknown/revoked key → 401 with `WWW-Authenticate: Bearer`; constant-shape error (do not reveal which case). `last_used_at` updated at most once per minute per key. Per-key rate limit: reuse the existing per-minute limiter keyed by key id (same `store_write_rate_per_min` budget); queue caps per key via the RunQueue client id `key:<id>`.
- Public REST (`/v1/api`, tag `public`), JSON only:
  - `POST /research` body `{question: str (same limits as AskRequest), mode: "deep"|"quick" = "deep", pack: str|None, plan: [{term, instructions}]|None, doc_ids: list[str]|None (mode becomes "docs" when given)}` → 202 `{run_id, session_id, turn_id, status}`. Guardrail refusals come back through the run like in the app.
  - `POST /plan` body `{question, mode, pack}` → the strategy plan `{reasoning, searches}` (wraps the existing plan_only path; no run).
  - `GET /runs/{run_id}` → `{run_id, status, kind, mode, pack, created_at, finished_at, error, answer: {content, references, records, doc_refs, empty_files, usage} | null, progress: {phase, searches, replans}}` — only for runs created with a key (any key; runs are not per-key private, matching the app's shared store; documented).
  - `GET /runs/{run_id}/events` → the existing SSE stream (resumable with `Last-Event-ID`/`after`).
  - `POST /runs/{run_id}/cancel` → only by the key that created it (403 otherwise).
  - `GET /runs/{run_id}/artifacts/{kind}` with kind `provenance` (JSON, same shape as the app's provenance file), `bibtex`, `ris` (text, generated server-side by a Python port of the frontend `bibliography.ts` rules — same escaping/encoding guarantees, with a parity test against shared fixtures).
  - `GET /packs` → the six packs (id, th, en names).
  - `GET /openapi.json` → OpenAPI 3.1 document containing only the `/v1/api` routes, with the bearer security scheme.
- The browser routes and their behaviour are unchanged; the public routes never accept `X-Client-Id` as identity.
- MCP (`mcp` package, exact pin in uv.lock; FastMCP, Streamable HTTP, mounted at `/mcp`, stateless): bearer key required (same dependency logic; 401 before any tool runs). Tools: `plan_research(question, mode?, pack?)`, `start_research(question, mode?, pack?, plan?)`, `get_run(run_id)`, `wait_run(run_id, timeout_seconds ≤ 600)` (polls the run until terminal or timeout; returns the same shape as get_run), `get_artifact(run_id, kind)`, `cancel_run(run_id)`, `list_packs()`. Tool descriptions in English, concise. Untrusted paper text is returned as data only (no instructions added).
- Python SDK `sdk/python` (package `ai_scientist_client`, pyproject with pinned httpx floor, Python ≥ 3.11): `Client(base_url, api_key)` with `plan`, `research`, `run`, `wait` (poll with backoff), `events` (SSE iterator), `cancel`, `artifact`, `packs`; typed dataclasses; raises `ApiError(status, code, message)`. README with a 10-line example. Tests run against the real FastAPI app via httpx `ASGITransport`? — no: the SDK is sync httpx; tests use `httpx.MockTransport` fixtures captured from the server shapes plus one integration test using FastAPI `TestClient` as the transport.
- `docs/api.md`: authentication, endpoints, examples (curl, SDK, MCP client config for Claude Desktop / any MCP client), rate limits, data visibility (shared store; no per-key privacy).
- Never read or print `.env` or secrets; never print a created key outside the CLI's own stdout. Commits end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; stage explicit paths.

## Review Focus

1. A revoked key stops working on the next request, for REST and MCP alike.
2. A key never appears in logs, error messages, provenance, or the DB in plain form.
3. API runs cannot cancel or flood browser runs (separate client ids; per-key caps).
4. `wait_run` / SDK `wait` with a run that stays queued past the timeout returns cleanly with the current status (no hang, no exception).
5. OpenAPI document lists exactly the public routes and validates (3.1).
